# way2AIPM OS v0.1 Product Spec

## 1. Product Positioning

way2AIPM OS is a personal operating system for AI PM job hunting and growth.

v0.1 focuses on one practical loop:

```text
Job Pipeline
  -> Pre-Interview Room
  -> Post-Interview Review
  -> Weakness Archive
  -> Training Plan
  -> Next Interview Validation
```

The product is private-first. It should help the user run real job-search work now, while preserving a clean structure that can later become a public portfolio and growth archive.

## 2. v0.1 Goal

Build a lightweight local system that helps the user manage AI PM job opportunities, prepare interviews, review real interview performance, capture weaknesses, and turn those weaknesses into training tasks.

v0.1 should not try to build the whole OS. It should prove that the core job-search improvement loop works.

## 3. Product Principles

### 3.1 Process over storage

The system should not be only a database of notes. Each module should represent a repeatable workflow with clear triggers, inputs, outputs, and completion criteria.

### 3.2 Private first, public later

The first user is the creator. Records can be rough, tactical, and private.

Future public output should come from selected, polished artifacts rather than from exposing the whole private system.

### 3.3 One loop before many modules

v0.1 only needs to support the main job-search loop. Other modules can appear later when the loop has been validated through actual use.

### 3.4 Evidence over feeling

Interview improvement should be tracked through concrete signals:

- Which questions were asked
- Which answers were weak
- Which ability gap caused the weak answer
- Which training task was created
- Whether the next interview showed improvement

## 4. v0.1 Scope

### 4.1 Included

- Dashboard / Control Center
- Job Pipeline
- Pre-Interview Room
- Post-Interview Review
- Weakness Archive
- Training Plan Center

### 4.2 Deferred

- Full AI frontier thinking framework
- Public portfolio product line

## 5. Core Modules

### 5.1 Dashboard / Control Center

#### Role

The dashboard is the lightweight v0.1 version of `00_总控调度器`.

It does not need real automation in v0.1. Its job is to show the current state and guide the next action.

#### Trigger

The user opens the system and wants to know what to do next.

#### Inputs

- Active opportunities
- Upcoming interviews
- Reviews waiting to be completed
- Open weaknesses
- Active training tasks

#### Flow

1. Identify urgent interview-related work.
2. Surface opportunities that need a next action.
3. Surface interviews that need preparation or review.
4. Surface unresolved weaknesses and training tasks.

#### Outputs

- Today's focus
- Upcoming interview list
- Follow-up opportunities
- Open training tasks

#### Completion Criteria

The user can answer: "What should I do next?" within 30 seconds.

#### Anti-Patterns

- Turning the dashboard into a decorative landing page
- Showing many charts before there is enough data
- Hiding urgent next actions behind generic summaries

### 5.2 Job Pipeline

#### Role

The Job Pipeline is the PMO layer for job hunting. It tracks opportunities, stages, priorities, risks, and next actions.

#### Trigger

- A new JD is collected
- A job is applied to
- An interview is scheduled
- The status of an opportunity changes

#### Inputs

- Company name
- Role title
- JD link or raw JD text
- Source
- Priority
- Current stage
- Risk level
- Next action

#### Flow

1. Create or update an opportunity.
2. Set current stage.
3. Mark priority and risk.
4. Link interview rounds and preparation materials.
5. Track the next action and due date.

#### Outputs

- Opportunity record
- Pipeline board or list
- Next action queue

#### Completion Criteria

Each active opportunity has a clear stage, priority, risk, and next action.

#### Anti-Patterns

- Treating all opportunities as equal
- Recording companies without a next action
- Losing the relationship between JD, preparation, interview, and review

### 5.3 Pre-Interview Room

#### Role

The Pre-Interview Room turns an interview invitation into a focused battle brief.

#### Trigger

- An opportunity reaches `invited` or `preparing`
- An interview round is scheduled

#### Inputs

- Opportunity
- Company information
- JD
- Interview round type
- User's project ammo
- Known weaknesses

#### Flow

1. Research company and product context.
2. Break down JD requirements.
3. Map JD requirements to user's projects and experience.
4. Predict likely questions.
5. Identify high-risk questions.
6. Create preparation checklist.

#### Outputs

- Company research notes
- JD analysis
- Question prediction list
- Project mapping
- High-risk question list
- Preparation checklist

#### Completion Criteria

Before the interview, the user has a concise brief covering company context, JD fit, likely questions, project stories, and risky gaps.

#### Anti-Patterns

- Preparing generic answers without reading the JD deeply
- Studying company news without connecting it to the role
- Listing questions without preparing answer structure
- Ignoring previously exposed weaknesses

### 5.4 Post-Interview Review

#### Role

The Post-Interview Review converts a real interview into evidence for improvement.

#### Trigger

- An interview round has just ended

#### Inputs

- Interview round
- Actual questions asked
- User's answers
- Interviewer reactions
- Self-rating
- Result, if available

#### Flow

1. Record actual questions as soon as possible.
2. Rate answer quality.
3. Identify strong answers and weak answers.
4. Analyze the cause of weak answers.
5. Create or update weakness records.
6. Create follow-up training tasks.
7. Update opportunity status.

#### Outputs

- Interview review
- Question log
- Answer rating
- Failure point analysis
- Linked weaknesses
- Linked training tasks

#### Completion Criteria

Every meaningful weak answer is connected to at least one weakness or training task.

#### Anti-Patterns

- Writing only emotional impressions
- Marking an interview as "bad" without identifying the failure point
- Creating vague weaknesses such as "expression is bad"
- Waiting too long and forgetting actual questions

### 5.5 Weakness Archive

#### Role

The Weakness Archive tracks recurring ability gaps exposed by interviews and preparation.

#### Trigger

- A post-interview review identifies a weak answer
- The same issue appears across multiple opportunities
- A training task reveals deeper capability gaps

#### Inputs

- Weakness title
- Category
- Evidence
- Frequency
- Severity
- Related questions
- Related opportunities
- Repair status

#### Flow

1. Create a weakness from evidence, not from vague feeling.
2. Categorize it.
3. Link it to real questions and interviews.
4. Decide whether it requires training.
5. Track whether it improves in later interviews.

#### Outputs

- Weakness record
- Weakness category view
- Repetition signal
- Repair status

#### Completion Criteria

The user can see which weaknesses are most damaging and whether they are being repaired.

#### Anti-Patterns

- Creating too many tiny weaknesses
- Creating abstract weaknesses with no evidence
- Never closing or updating repaired weaknesses
- Confusing symptoms with root causes

### 5.6 Training Plan Center

#### Role

The Training Plan Center turns weaknesses into concrete repair tasks.

#### Trigger

- A weakness needs repair
- An upcoming interview requires targeted practice
- A repeated question needs stable expression

#### Inputs

- Weakness
- Target ability
- Training task
- Acceptance criteria
- Due date
- Practice output
- Validation result

#### Flow

1. Convert a weakness into one or more training tasks.
2. Define acceptance criteria.
3. Practice with a concrete output.
4. Mark the task as completed only after review.
5. Validate the improvement in later interview preparation or real interviews.

#### Outputs

- Training task
- Practice output
- Acceptance result
- Validation note

#### Completion Criteria

Each active training task has a clear target, expected output, acceptance standard, and status.

#### Anti-Patterns

- Creating tasks like "improve communication" without concrete output
- Marking tasks done without validation
- Practicing unrelated topics while urgent interview risks remain open

## 9. MVP User Flow

```text
1. Create an opportunity from a JD
2. Set stage, priority, risk, and next action
3. Move opportunity to invited/preparing
4. Create interview round
5. Complete pre-interview brief
6. Finish real interview
7. Record actual questions and answer ratings
8. Create weakness records from weak answers
9. Create training tasks from weaknesses
10. Use later interview results to validate improvement
```

## 10. v0.1 Non-Goals

- No multi-user support
- No public publishing workflow
- No automated web crawling
- No AI-generated analysis as a required dependency
- No complex analytics dashboard
- No mobile-first native app
- No full content management system

## 11. Open Product Questions

1. Should v0.1 store data in local browser storage, Markdown files, or a lightweight database?
2. Should records be optimized for quick capture first or structured completeness first?
3. Should the first UI be a single-page local app or a small routed web app?
4. Which views matter more at the start: pipeline board, detail forms, or review workflow?
5. Should AI assistance be introduced in v0.1, or should v0.1 first establish manual workflows?
