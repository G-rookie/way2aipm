# v0.24 OpenClaw 受控 Agent 执行链路验证记录

## 状态

- 日期：`2026-05-27`
- 分支：`codex/feature-agent-execution-v0.24`
- 当前结论：`evaluate_langgraph`
- 完成范围：两个 Agent 工作区、确定性本地模型桩、OpenClaw 原生子 Agent 委派、复盘只读/提案工具调用与无业务写入验证。
- 不通过范围：严格的父/子 Agent 工具权限隔离，以及使用 `sessions_yield` 等待子任务回传的稳定性。

## 验证目标

v0.24 试图验证以下最小结构能否作为正式领域编排基础：

```text
orchestrator
  -> review_specialist
  -> way2aipm_review_context
  -> way2aipm_propose_review_diagnosis
  -> approval required
```

理想权限边界为：总控 Agent 只拥有委派工具，复盘专项 Agent 才拥有领域读取与提案工具。

## 实现方式

### Agent 工作区

| Agent | 工作区文件 | 责任 |
| --- | --- | --- |
| `orchestrator` | `integrations/openclaw/agents/orchestrator/AGENTS.md` | 接收 `workflowRunId` 并委派诊断任务 |
| `review_specialist` | `integrations/openclaw/agents/review_specialist/AGENTS.md` | 读取复盘上下文并提交待审批候选 |

实验 Runtime 令两个 Agent 使用 `skills: []`，不注入无关 skills。

### 可重复烟测

新增：

```text
integrations/openclaw/agent-delegation-smoke-test.mjs
```

该测试：

1. 在 `tmp/openclaw-v024/` 生成隔离 OpenClaw 配置与 session 状态。
2. 启动本地 way2AIPM 服务、本地 OpenAI-compatible 确定性模型桩与 OpenClaw Gateway。
3. 创建一条临时 `diagnosis_pending` 工作流。
4. 通过真实 `openclaw agent --agent orchestrator` 执行委派。
5. 让专项 Agent 真实调用 v0.23 的两个插件工具。
6. 校验审批状态与无业务写入结果。
7. 逐个删除测试创建的 Markdown 领域记录。

模型桩只负责按验证路径产生工具调用，Gateway 与插件 API token 默认在进程内随机生成且不落入跟踪文件。因此该测试证明 Runtime 行为和权限边界，不评估真实模型的诊断质量。

## 关键限制

### 父子工具隔离不满足

在严格配置中，`orchestrator` 只允许 `sessions_spawn`、`sessions_yield` 与 `session_status`，而 `review_specialist` 只允许两个 way2AIPM 插件工具。真实运行失败，并给出以下有效含义的错误：

```text
No callable tools remain ... inherited tools.allow: sessions_spawn, sessions_yield, session_status
```

这是因为 OpenClaw 原生 `sessions_spawn` 的子 Agent 会继承父 Agent 的 allow 边界，子 Agent 无法获得父 Agent 未拥有的领域工具。

为完成执行链路证明，本轮只能让总控 Agent 的 allow 集合同时包含两个领域插件工具，再通过 `AGENTS.md` 要求它不调用这些工具，并用专项 Agent 的最终过滤层限制子任务。这个方案能跑通，但不符合“总控在权限层完全看不到领域工具”的严格要求。

### `sessions_yield` 回传出现写锁竞争

当总控 Agent 在委派后调用 `sessions_yield` 等待专项结果时，本地实验出现父 session 写锁超时：

```text
SessionWriteLockTimeoutError: session file locked (timeout 60000ms)
```

为了单独验证委派与工具边界，本轮采用总控提交异步委派后结束当前轮次、烟测等待专项结果的方式。该方式证明子任务执行可行，但没有证明 OpenClaw 在本场景下可稳定承担同步等待/恢复编排。

## 技术结论

OpenClaw 仍可作为受控 Agent 执行层候选，且其 Tool Plugin 边界可以复用；Lobster 也已经证明具有独立审批能力。但当前原生多 Agent 委派不能满足本项目期望的严格角色工具隔离，回传等待路径还存在稳定性问题。

因此 v0.24 不将 OpenClaw 采纳为正式闭环编排 Runtime，`WorkflowRun` 继续作为唯一领域状态来源；下一步转为针对性验证 LangGraph 的子图工具隔离、interrupt 审批与状态幂等能力，并保留已经实现的 Tool Adapter 作为对照接口。

## 后续建议

1. v0.25 编写 LangGraph 对照验证规格，复用同一条复盘诊断流程和无写入断言。
2. 验证 `orchestrator` 节点与 `review_specialist` 节点能否配置不同工具集合，而不会发生父级权限扩张。
3. 验证审批 interrupt/resume 与 `WorkflowRun.id` 的一对一、幂等关联。
4. 只有对照验证满足严格边界后，再引入真实模型评价候选质量。
